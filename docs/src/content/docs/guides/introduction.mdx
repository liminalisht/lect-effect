**lect-effect** is organized around a simple idea:

> **Make the domain canonical, then reindex everything else against it.**

Concretely, the domain is expressed as **Effect Schema** objects (runtime validation + static types), and computations are expressed as **Effect** programs whose requirements are explicit in the type parameter `R` of `Effect<A, E, R>`.

GraphQL is not the “center” of the system; it is a **view** (a representation) of the domain, constructed by *weaving* resolvers and schemas via **GQLoom**.

If you like categorical language: the codebase is biased toward making the *Kleisli category* of `Effect` the primary arena of composition, while GraphQL is a boundary functor from “requests” into that Kleisli category.

---

## Project goals

1. **Single source of truth for types and validation**
   Domain value objects and DTOs are defined as `Schema`s; TypeScript types are derived from those schemas.

2. **Explicit dependencies, compositional construction**
   Every computation declares what it needs as `R` (a union of services); services are provided by a `Layer` graph.

3. **Transport layer stays thin**
   GraphQL resolvers should be small adapters: decode input, run a handler, return output.

4. **Testability by construction**
   Property tests for schemas, handler tests for semantics, and GraphQL-level tests for end-to-end behavior.

5. **Docs as a build artifact**
   JSDoc is part of the interface: `docgen` turns it into navigable reference material.

## Mental model (how to read the code)

Think in four strata, each a different “presentation” of the same underlying intent:

1. **Domain (`src/domain/`)**
   Value objects and composite structures as `Schema`s (and their inferred types).

2. **Services (`src/services/`)**
   Abstract capabilities (tags) living in an Effect `Context`.
   These are the *objects of dependency*, referenced by handlers and repositories.

3. **Layers (`src/services/layers/`)**
   Concrete constructions of services, assembled into a dependency DAG.

4. **Boundary (`src/graphql/`)**
   GraphQL schema + resolvers, woven from the above and executed by injecting an `Effect` runtime into GraphQL context.

## Quickstart (local dev)

### 1) Install dependencies

```bash
pnpm install
```

### 2) Start Postgres

The repo includes `docker-compose.yml` with two databases:

* `masterdatadb` on port **5432**
* `test_masterdatadb` on port **5433**

```bash
docker compose up -d
```

### 3) Set environment variables

Config is read through Effect `Config` and typically provided by `.env` / `.env.test` via `dotenv` + `env-cmd`.

**App (prod/dev)**

* `BACKEND_PORT` (default: 4000)
* `BACKEND_ENV` (one of `dev | test | staging | prod`)
* `BACKEND_LOG_LEVEL` (default: Info)
* `MASTERDATA_PG_URL` (required)
* `MASTERDATA_PG_POOL_MIN` (default: 0)
* `MASTERDATA_PG_POOL_MAX` (default: 10)
* `MASTERDATA_PG_IDLE_TIMEOUT_MS` (default: 30000)

**Tests**

* `TEST_BACKEND_PORT` (default: 3000)
* `TEST_BACKEND_ENV`
* `TEST_BACKEND_LOG_LEVEL`
* `TEST_MASTERDATA_PG_URL`
* `TEST_MASTERDATA_PG_POOL_MIN`, `TEST_MASTERDATA_PG_POOL_MAX`, `TEST_MASTERDATA_PG_IDLE_TIMEOUT_MS`

Example URLs matching `docker-compose.yml`:

* `MASTERDATA_PG_URL=postgres://user:password@localhost:5432/masterdatadb`
* `TEST_MASTERDATA_PG_URL=postgres://testuser:testpassword@localhost:5433/testmasterdatadb`

### 4) Run the guided wizard (recommended)

```bash
./lect-effect.sh --wizard
```

The wizard will walk you through the typical local flow (install, migrate, start) and surface the right subcommands.

### 5) Manual commands (if you prefer)

```bash
./lect-effect.sh start
```

You should see a log like:

* `graphql server is running on http://localhost:<port>/graphql`

- Discover commands: `./lect-effect.sh --help`
